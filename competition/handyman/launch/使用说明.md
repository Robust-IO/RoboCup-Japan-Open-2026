# Handyman 比赛包使用说明

更新日期：2026-11-27。本文件统一替代原启动、任务配置、动态任务和物品抓取配置说明。以下命令均在 Ubuntu/WSL 终端执行。

## 1. 比赛包位置

Ubuntu：`~/RoboCup-Japan-Open-2026/build/handyman-competition`

Windows 文件管理器：

```text
\\wsl.localhost\Ubuntu\home\crazylearner\RoboCup-Japan-Open-2026\build\handyman-competition
```

每次新开终端先进入：

```bash
cd ~/RoboCup-Japan-Open-2026/build/handyman-competition
```

本包是部署目录，开发目录中的修改不会自动同步到这里。系统仍需 ROS 2 Humble、系统 Python、GPU 驱动、系统库和通往 Unity 的网络。本包不包含完整 Unity 项目或 Handyman.exe。

## 2. 启动顺序：先 Ubuntu，后 Unity

1. 确认 Unity 将从 session1 开始，机器人处于该轮初始位置、空爪。
2. 进入比赛包，先运行自检：

```bash
./check_competition.sh
```

自检检查六轮配置、模型、ROS 包、桥接二进制/动态库及真实入口参数，不启动比赛、不发机器人动作、不清理旧进程。检查正常退出并显示 passed 后继续；自检不等于实测成功。

3. 从下表选择一个模式启动，只运行一个入口。
4. 保持 Ubuntu 终端运行，再在 Unity 编辑器 Play 或 Build 的 exe 中开始 session1，等待新的准备握手和任务指令。

| 模式 | 适用情况 | 启动命令 |
|---|---|---|
| 固定任务 | 按预先配置的六轮任务和匹配句子执行 | `./start_fixed.sh` |
| 动态任务 | 解析实际收到的任务句子并确定物品、起始家具和目的地 | `./start_dynamic.sh` |

两个入口始终从 session1 开始，不再接受起始轮次位置参数。Unity 也必须从 session1 的初始位置、空爪状态开始。兼容入口 `./start_competition.sh` 无参数时仍为固定模式，默认完整执行六轮。

## 3. 用 N 控制正常执行的轮数

`N` 默认是 6，范围为 0～4294967295，与 Interactive Cleanup 的 uint32 参数范围一致。支持 ROS launch 风格的 `N:=数量`，也支持 `--N 数量`：

```bash
./start_dynamic.sh N:=2
# 等价于 ./start_dynamic.sh --N 2

./start_fixed.sh N:=2
```

以上命令均从 session1 开始：前两轮按原有逻辑正常执行；从第三轮起，完成准备握手并回复 `I_am_ready`，收到该轮首次 `Instruction` 后按单调时钟等待 5 秒，发送一次 `Give_up`，再等待 Windows 的任务结束消息及下一轮新握手。这些放弃轮次不启动导航、定位或抓取任务。

- `N=0`：六轮全部按上述时序放弃。
- `N=6` 或更大：六轮全部正常执行。
- `N` 是正常执行的轮数，不是起始轮次，也不是直接跳转或减少 Windows 的轮数。
- 重复 `Instruction` 不重置计时；`Corrected_instruction` 不启动计时。
- 收到 `Task_failed`、`Task_succeeded`、`Mission_complete`，或用户退出时，取消尚未发送的放弃消息。
- `./start_dynamic.sh 3` 等旧位置参数会报错，不会被解释成 `N=3`。
- `start_fixed_session1.sh` / `start_dynamic_session1.sh` 是对应入口的别名，可传入 `N`；旧 session2～6 快捷入口已禁用并显示迁移提示。

协议消息名称是 `Give_up`，`detail` 为空。放弃会使 Windows 将该轮判为失败，不是暂停；本程序不伪造 `Task_finished` 或自行宣布成功。每次重启从第一轮重新开始，不支持中途持物恢复。

## 4. 退出、清理和重启

在启动终端输入 `q` 或 `exit` 后回车，或者按 `Ctrl+C`。等待清理完成再重启；不要同时运行两个控制入口，也不要同时运行原开发目录的控制程序。

正式启动会自动清理确认属于旧 Handyman 的进程，检查 TCP 9090、50001 和控制锁，再校验并应用六轮配置。未知程序占用端口时会报告并拒绝启动，不自动杀其他应用。

只检查占用：

```bash
python3 competition_cleanup.py
```

单独清理旧任务：

```bash
python3 competition_cleanup.py --execute
```

不要删除控制锁文件来伪造释放。启动新任务意味着清理旧任务，不是恢复断点。

退出时清理本次进程、包内 `.tmp/r-*` 临时目录及短路径 `/tmp/hm-ipc-*` 模型通信目录；清理未完成会保留目录并提示。日志、图片、配置、模型和审计备份不自动删除。断电或强制杀死入口可能留下残余，下次启动会重新检查。

跨轮由 Unity 新握手驱动。旧轮迟迟不退出时会升级清理旧任务及子进程，确认退出后才启动下一轮。

## 6. 修改固定任务

编辑根目录 `competition_tasks.json`：

- `target`：物品类别，合法名称见 `project/training/dataset.yaml`。
- `source.room`、`source.furniture_id`：物品所在房间/家具，不是机器人出生位置。家具 ID 带房间，如 `dining_table#lobby`。
- `destination.room`、`destination.furniture_id`：目的房间/家具。
- `destination.mode`：支撑面用 `table_place`，垃圾桶用 `container_drop`，既有 session3 递交用 `avatar_handover`。
- `expected_instruction`：固定模式期望完整句子，改任务时同步修改。仅规范化大小写、多余空格和末尾句号，不理解任意新句式。
- session3 的 `initial_target` 与初始句子用于首次搜索；`target`、`source`、`corrected_instruction` 用于真实修正指令后的任务。

只验证：

```bash
./configure_tasks.sh
```

`validated: 6` 表示六轮通过；`applied: false` 表示未应用；`drop_recovery_sessions: [2,5,6]` 表示这三轮启用掉落重拾；`robot_commands_sent: false` 表示没有发送动作。

停止任务后可手动应用：

```bash
./configure_tasks.sh --apply
```

应用前会校验六轮并备份，运行中拒绝应用。正常启动自动应用，无需每次手动操作。不要只修改生成的运行配置，下一次应用可能覆盖它。

更换物品和家具需要实测。新垃圾桶需在 `config/container-geometries.json` 中提供对应 `Layout|家具ID` 标定，不能借用其他桶坐标。Moderator 当前使用 LayoutA 的既有接收区域，新位置需补标定。固定 session3 的首次搜索成功分支不能视为与动态模式完全等同。

## 7. 动态指令和搜索

支持的基本句式：

```text
Go to [the] 房间, grasp [the] 物品 [on/in [the] 起始家具]
and put/throw/give ... on/in/into 目的家具 / to me.
```

支持常用冠词、大小写、名称下划线/空格等规范化，不是任意自然语言理解。未知名称不猜测替换；同名目的家具优先用明确目的房间，否则要求任务房间内唯一匹配。near/close to/next to 不是通用空间关系推理能力。

搜索顺序：

1. 明确给出起始家具，先观察该家具。
2. 未指定家具且预设记录有唯一绑定，先观察绑定家具。
3. 无绑定、绑定处没找到或记录不完整，转查房间候选家具，再主点/备用点扫描。
4. 完整记录中没有目标，也必须进房间实际扫描，不能仅凭静态表上报不存在。
5. 完整扫描结束且无未解决候选后才发送 `Does_not_exist`，等待真实 `Corrected_instruction` 再解析。

房间扫描为平视、俯视30度两挡连续环视；长宽比不超过1.35只用主点，否则主点和备用点。证据不足或目标无法绑定支撑家具不等于物品不存在。

两种模式共用观察候选生成、导航排序、观察和抓取执行器。动态确认成功后交接观测，不重复独立扫描。候选家具搜索使用有限观察周期，以便继续其他家具。当前观察位置的接近和展臂路径可行时直接靠近抓取，否则选择抓取位姿及允许的侧向偏移。观察位置不是最终闭爪位置。

### 更新 Unity 物品绑定记录

取得实际项目 `SIGVerseConfig/Handyman/EnvironmentInfo01.json` 至 `EnvironmentInfo06.json`，放在同一目录。先确保地图和 Layout 配置匹配，再运行：

```bash
python3 workspace/training/session1/build_room_inventory.py /mnt/d/handyman/handyman-unity2/handyman-unity2/Build/SIGVerseConfig/Handyman
```

末尾改为实际六个 JSON 的目录，不需复制整个 Unity 项目。输出为 `config/room-inventories/session1.json` 至 `session6.json`。导入器使用 `graspablesPositions` 确定房间和家具绑定，不以配置答案代替真实指令，也不以导出位置替代实时 RGBD 抓取定位。

随机摆放或人工移动可能使表过时，现场搜索用于兜底。比赛运行中不要改写地图和绑定记录。

## 8. 抓法及掉落重拾

`config/object-grasp-profiles.json` 按目标类别绑定通用抓法和专属覆盖，两种模式一致：dog_doll/rabbit_doll 使用不规则模板；canned_juice/tumbler 使用圆柱身部模板；filled_ketchup 使用窄颈模板及专属放宽；其他类别沿用通用形状规则。

番茄酱覆盖包含小可见表面、配准累计位移、接触带深度及当前点云与接触垫重叠跨度相关放宽，不套用到其他物品。放宽不等于抓住，仍需闭爪和抬升后夹持验证。修改后重启任务加载，不热更新。

掉落重拾仅 session2、5、6：连续夹爪开度异常后停车复核，确认空爪则尝试寻找附近地面的同类物品，重抓后继续原目的地。无每15秒固定停车；开度不变的滑落可能漏检，不能认为覆盖所有掉落情况。

## 9. 日志及排障

新日志在包内 `runs/`，`logs` 是指向它的链接，旧 D 盘记录不会自动迁入。

```bash
cat runs/sessions123456-latest.txt
```

输出目录中的主要文件：

| 文件 | 用途 |
|---|---|
| `events.jsonl` | 官方指令、成功/失败和轮次衔接 |
| `supervisor-state.json` | 当前轮次和进程状态 |
| `sessionN/live.log` | 主程序状态与异常 |
| `sessionN/task/live-state.json` | 阶段、目标和停止原因 |
| `sessionN/task/journal.jsonl` | 动作及恢复过程 |
| `sessionN/task/command-*.log` | 子命令输出 |
| `sessionN/task/session-result.json` | 退出后的结果，未退出时可能没有 |
| `sessionN/task/resolved-task-*.json` | 动态解析的指令和搜索路线 |

以官方 `Task_succeeded`/`Task_failed` 为判定，不把日志刷新视为实际有进展。不动时查看阶段、最后动作、恢复原因及子命令日志，保留整轮记录。不要重复启动多个入口强行推进。

一直等握手时，检查 Unity 起始轮、网络和是否已错过准备阶段。配置报错先修改配置再校验；端口/锁占用先退出旧任务并清理，不删除锁文件。

再次搬迁前停止比赛进程，完整移动并保留 `.package-root.json` 等隐藏文件。搬迁后从新位置运行自检；入口自动重定位包内文本路径，历史日志和审计不改写。跨机器仍需安装系统依赖。

本次实际迁移已通过包自检。最近导航恢复修复通过629项离线测试，并使用历史失败位置完成脱困重放。这不代表最新版本已通过六轮在线验收，比赛前仍需全流程复测。

模型通信使用本次运行专属的短路径 `/tmp/hm-ipc-*`，避免包目录过长超过 Unix socket 限制；数据和日志仍在包内。自检包含实际 socket 绑定。收到任务前初始化失败时等待新握手重试，最多3次，耗尽后明确报错退出。

启动准备阶段的时钟检查或导航初始化超时会清理该次服务，等待新握手重试同一轮，最多3次，耗尽后明确报错。时钟校准仍要求静止、单一来源、连续新样本；通过原生同步通道校准后重新验收，不直接接受未来时间戳。新桥接配置需重启比赛入口并让 Unity 重新连接后生效。


### 搬运掉落恢复（2026-11-27 更新）

仅 session2、5、6 启用，固定和动态任务共用。确认空爪后，头部俯视约46°，在中间、左34°、右34°各取两帧查找地面目标。第一轮未找到时，沿机器人后方后退0.5米，再进行一轮相同扫描。找到稳定目标则调用地面重拾，验证夹持后继续原目的地导航；两轮均未找到时，在运动停止确认后发送一次 `Give_up`，等待 Moderator 结束本轮。此结果不会上报 `Does_not_exist` 或 `Task_finished`。更新需重新启动比赛进程生效。
