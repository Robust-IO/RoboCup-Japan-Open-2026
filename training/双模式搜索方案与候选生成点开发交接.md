## 2. 背景、动机与边界

比赛前可能公开 Unity Layout，但尚不确定是否包含完整的 `GraspingCandidatesPositions`，也不确定工作人员是否会在任务制作中移动某些生成点。房间主点与备用点扫描也可能遗漏家具背面、隔断另一侧或高低处物体。

因此两种搜索计划必须能够独立使用，并可串联：候选点负责有针对性的预搜索，房间搜索提供不依赖候选位置完整性的后续搜索。双方案降低遗漏风险，但不构成“绝对无死角”保证。

用户的明确选择不是二选一的两个互斥算法，而是一个布尔开关：

- false：只运行主点＋备用点方案。
- true：先运行候选生成区域预搜索；若未确认目标，继续主点＋备用点方案。
- 任一阶段确认目标后结束本次搜索，交给既有目标确认／抓取接口；不继续无意义遍历。
- 候选点缺失或不可信时仍有房间方案可用。

范围限定：只改变搜索计划来源和调度，不重做协议、导航、模型推理和抓取系统；不读取正式任务答案来代替视觉识别，不增加比赛时从 Unity 获取物品真值的通道。

## 3. 配置契约

建议将下列参数纳入项目统一搜索配置；最终文件路径在实施时按现有配置体系决定：

```yaml
search:
  enable_candidate_presearch: false
```

参数语义固定，不能后续悄悄改成“true 时只搜索候选点”。

| 参数值 | 顺序 | 候选数据是否必需 |
| --- | --- | --- |
| false | 主点 → 备用点 → 既有按需补看／结果审查 | 否，不因缺少候选文件阻止启动 |
| true | 候选区域 → 未确认则主点 → 备用点 → 按需补看／结果审查 | 可缺失；记录原因并回退 |

配置缺省为 false，保持当前房间搜索行为。解析应校验真正的布尔值，避免字符串 `"false"` 被当作真值。非法配置应明确报错，不默默选择模式。

每个任务启动时固化本次模式、配置摘要、地图版本和候选数据版本，写入日志。运行中不因编辑配置文件而无声改变当前任务；新配置在下一任务生效。

候选数据出错可回退，但公共基础设施出错不能靠回退掩盖：例如候选清单地图指纹错误可以弃用候选清单；实时定位或整个导航地图身份不可信则必须走原有安全处理。

## 4. 状态与转移

```text
任务绑定／房间约束／地图与传感器检查
                    |
         enable_candidate_presearch
            / false         \ true
           |                 候选数据验证
           |                   |
           |             候选区域观察与复核
           |                 /       \
           |             确认目标    未确认／数据不可用／阶段预算不足
           |                |         |
           +--------------------------+
           |
      主点扫描 → 备用点补看 → 必要补看与未决候选复核
           |                         |
        确认目标                  搜索完成审查
           |                         |
     交付目标证据           未发现但证据充分／覆盖不足／执行故障
```

图中“确认目标”直接退出搜索，不再进入下一搜索阶段。所有阶段都遵守任务取消、Session 结束、修正指令和故障停止。

实现时建议用明确的阶段状态而非多个相互覆盖的布尔量。阶段名可采用 `CANDIDATE_PRESEARCH`、`ROOM_PRIMARY`、`ROOM_BACKUP`、`SUPPLEMENT`、`REVIEW`，但应兼容现有运行器。

预搜索失败不等于整个任务失败。以下事件要区分记录：无候选数据、版本不匹配、候选区域看完未确认、部分区域遮挡、局部路径暂不可达、预搜索预算结束。不要把这些都记成物品不存在。

## 5. 两种方案共享什么

共享现有：任务身份与请求绑定、地图验证、房间约束、Nav2 执行、门洞策略、转向与稳定检测、头部动作、RGBD／TF 时序验证、模型推理、目标近距离复核、候选去重、取消与停止、日志及恢复机制。

独立的部分只应是“观察区域与位姿如何生成”和“这些观察任务的调度顺序”。避免复制两套执行器导致导航或安全修复只落在其中一套。

不要清空预搜索的有效候选后再从头检测；也不要把旧任务、旧 Session、重启前场景的证据拿来跳过新任务观察。

## 6. 主点＋备用点方案的要求

该方案不依赖候选点文件即可工作，仍是当前首要开发目标。

- 主点：在房间内选择可达、安全、能获得较多有效观察的位姿，不机械使用几何中心。
- 备用点：优先看见主点被遮挡的区域，尤其柜体将房间分成两部分时，要进入另一部分的可达内部区域，而不是落在分割线上。
- 保留历史 LayoutB 客厅测试教训：与主点有距离不等于获得新视野；仅在隔断边缘可能仍看不到目标。
- 环视方向数、重叠角度、俯仰角应沿用并核实已验证配置，不因本文件重新固定为六个方向或重新引入已修复的转向抖动。
- 主点和备用点完成不自动等于全房间可见。桌下、高柜顶面、柜后等未看清区域应标记并按需要补看。
- 目标必须通过指定房间约束，不能把相邻 lobby 高柜上的同类物品当成 living room 的目标。
- 不扩大“故障防护”范围拖延现场搜索验证；复用既有机制，针对搜索链路的实际缺口补齐。

## 7. 候选生成点方案的后续设计

### 7.1 Unity 导出

在独立项目副本或工具工作流导出静态候选信息，不改比赛场景、原物品材质和任务答案。是否允许利用这些信息须依据赛事确认。

注意拼写：层级父节点常为 `GraspingCandidatesPositions`；当前示例代码选择的 Tag 是单数 `GraspingCandidatesPosition`。用户文字中的 `GraspingCandidatesPositons` 是可能的拼写变体，不能拿它当唯一查找键。

拟导出信息：schema 版本、工具版本、Layout 标识、场景来源指纹、单位与坐标系、点稳定标识／层级路径、世界位置与旋转、必要尺寸、生成位置修正所需字段、房间区域依据、可获取的承载区域几何。

当前示例随机生成公式是世界位置减去 `(0, localScale.y * 0.49, 0)`，朝向来自世界旋转。此为本次审计结果，不是永恒协议；对新工程重新核实。不要只导出 localPosition 或忽略父变换。

需处理未激活 Layout、运行时隐藏的候选标记、重复标识、跨房间／无房间点。不要把只读到了当前活动 Layout 当成成功导出全部 Layout。

### 7.2 Ubuntu 导入与观察位姿生成

1. 校验来源、字段、数值、Layout、地图对应关系和单位。
2. 使用现有地图导入坐标变换，不凭经验另写一套 Unity→ROS 轴映射。
3. 按实际房间区域归属，不仅看节点路径名称；边界和重叠需给出诊断。
4. 将同一承载面附近的点合并为区域，优先减少观察次数。
5. 结合机器人 footprint、当前连通性、相机高度／俯仰／视场与遮挡生成观察位姿。
6. 以新增有效覆盖和路径代价排序；运行时再检验路径及动态障碍。
7. 观察覆盖应包含合理的点周边／承载面，不把精确生成坐标作为唯一检测小窗口。

两个常见陷阱：地面二维空闲不意味着相机到物体之间无遮挡；所有候选点各到过一次不意味着它们都被有效观察过。

### 7.3 预搜索终止与回退

找到并确认目标则成功结束搜索。其余未确认情形转入房间搜索；保留被遮挡、未决与尚不可达区域的记录，以便后续复核。

为房间搜索及后续抓取／放置保留任务时间。预搜索预算应依据剩余 Session 时间和实际耗时配置／标定，不在文档里发明固定秒数。阶段预算不允许变相恢复此前导致导航过早失败的短固定超时。

## 8. 证据共享与重复抑制

至少区分：未观察、清晰观察未检出、遮挡／质量不足、疑似目标待复核、确认目标、已排除的实例、观察位姿暂不可达。名称可复用现有枚举。

记录粒度是区域和物体实例，而不只是“访问过的点”。记录任务／Session、Layout 与地图摘要、房间、观察位姿、相机姿态、时间、图像质量、RGBD／TF 有效性、覆盖依据和目标实例证据。

不能用以下条件单独跳过房间观察：同一导航点到过、附近生成点访问过、机器人曾朝这个方向转过、某一帧没有检测。

只有证据新鲜且确实覆盖相同区域时，才能消除重复观察。初版可保守地保留主点／备用点扫描，只复用候选记录；先证明正确，再优化跳过规则。

对有位置关联歧义、同类密集物体、动态遮挡的情形保守保留，不因去重而丢掉真实目标。YOLO 分数不是校准后的存在概率，不直接使用固定 80% 作为唯一确认标准。

## 9. 不存在判断及任务变化

候选预搜索模块绝不能自行发送 `Does_not_exist`。最终结果交给既有协议协调器，根据完整搜索证据与当前状态判断。

必须区分：确认目标、充分搜索未发现、覆盖不足、执行故障／取消。不可达、客人挡路、无深度、相机断流、预算用尽都不是“不存在”的充分证据。

此前讨论过的“不可达房间等同目标不存在”不作为实现依据。当前示例判分实现中，错误的 `Does_not_exist` 会失败；正确报告后可能收到 `Corrected_instruction` 并继续任务。

修正指令改变目标／房间时重新绑定任务语义；类别相关排除证据失效，几何覆盖证据是否可复用必须重新验证。新 Session、场景重启、地图变化需隔离或失效旧记录。旧回调不能启动下一阶段运动。

若将来出现不指定房间的任务，需独立核实协议及搜索范围，再设计跨房间调度；本次不默认实现全地图最短遍历。

## 10. 第一阶段验收门槛：先完成房间方案

以下是待核实／待完成清单，不是已通过声明：

- [ ] 不需要候选点数据，从 Session 初始位置接收真实任务并进入正确房间。
- [ ] 自动到主点、完成有效环视、复核候选；找不到时自动转备用点，无需逐步人工“下一步”。
- [ ] 主点被遮挡而另一分区可见的目标，备用点能有效检出；多次摆放测试，不以偶然成功代替稳定性。
- [ ] 相邻房间同类物品被过滤，过滤后继续本房间搜索。
- [ ] 疑似目标被否定后继续搜索，不能提前结束或无限反复复核。
- [ ] 目标不存在与覆盖不足能区分，协议行为与预期一致。
- [ ] 客人短暂挡路、图像无效、取消／Session 切换不会产生错误不存在或遗留运动。
- [ ] 对已选测试 Layout 和可达房间有现场证据；明确未测试与不纳入范围的区域，不宣称所有地图全覆盖。
- [ ] 留存结果、失败样例、覆盖与耗时记录，用户确认主点＋备用点搜索闭环已全程跑通。

“全程跑通”在此指完整搜索任务闭环，不擅自宣称阶段 5／6 的抓取放置已经完成。若用户要求完整取放比赛闭环，应另行明确依赖与验收范围。

## 11. 第二阶段实施顺序与验收

1. 审核最新代码，确定统一配置入口；加入默认 false 的开关，并证明 false 路径与原方案一致。
2. 定义带版本的候选数据格式、导出和坐标转换；用小型样例核对，再验证多 Layout。
3. 实现离线区域合并、房间分配和观察位姿生成，可视化检查覆盖，不连接 Unity 发运动。
4. 将候选观察任务接入现有执行器，保持相同安全与证据门槛。
5. 接通未找到后的房间方案回退，加入任务取消／恢复的阶段记录。
6. 用真实场景测试候选内目标、候选外目标、遮挡、缺失文件及版本不匹配。
7. 正确性稳定后再做覆盖去重与路径优化；记录时间收益与漏检代价。

| 测试情形 | 必须结果 |
| --- | --- |
| false，候选文件不存在 | 正常执行原房间搜索 |
| false，候选文件损坏 | 不依赖该文件，原方案不受影响 |
| true，候选点可见目标 | 确认后退出搜索，不再多跑房间方案 |
| true，候选点均未确认 | 自动进入主点／备用点，不发送不存在 |
| true，目标被移到候选覆盖外 | 通过房间方案继续寻找 |
| true，候选数据缺失／Layout 不匹配 | 明确日志并回退，不静默套用其他地图 |
| 主点遮挡、备用点可见 | 能切换并确认目标 |
| 两阶段均被遮挡或相机失效 | 覆盖不足／故障，不误报不存在 |
| 房外同类目标 | 不作为指定房间目标 |
| 阶段切换时取消或重启 | 无旧阶段遗留运动、无重复任务发出 |
| 预搜索预算结束 | 安全收尾后进入房间阶段，整轮截止时间不重置 |

## 14. 操作约定与交接结论

- 不需要 Unity 时先做离线工作；需要真实传感器或机器人运动时提前通知用户恢复 Unity，避免消耗 Session 时间。
- 数据、更新包及可视化尽量保存 D 盘，不占用 C 盘；ROS 项目仍使用现有 WSL 仓库。
- 不删除旧数据或修改原比赛场景；不因本设计提交／推送／合并 Git，除非用户另行要求。
- 当前交付仅为本文件。未来实现进度应附日期、代码位置、测试证据，不覆盖用户原始决策。

最终决策：**先跑通主点＋备用点；以后用 `enable_candidate_presearch` 控制是否在其前面加候选生成区域预搜索。true 必须保留未确认时的房间搜索回退，false 必须完全不依赖候选点。**
